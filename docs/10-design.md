# Design

The routes are listed in `20-routes.md`.

Agbredo shows what a fleet of existing GitHub Actions agents did and what they cost.
## Parts

- **Telemetry step** (runs in the agent's workflow, before each Claude Code step). Gets a token from the server with the job's OIDC token, then points Claude Code's own OpenTelemetry export at the server. No wrapper or sidecar. See `integrations/claude-code-otlp/`. It is the only way usage reaches Agbredo.
- **Server** (Go, one process). Serves the dashboard, takes telemetry and GitHub webhooks, polls GitHub every 30 seconds for runs that have not finished, and asks GitHub for the jobs of runs that have (see Jobs and steps).
- **PostgreSQL.** The store for the dashboard. Records are JSON documents in `jsonb` columns.
- **Telemetry store** (optional, OpenObserve on Railway's private network). Keeps the full telemetry for later analysis, and the raw payload of every GitHub webhook delivery that the server accepts (see Webhook flow). Only Agbredo can reach it. See `internal/forward/`.

## Flow

1. An agent's workflow runs on its own trigger (schedule, push, manual).
2. Before each Claude Code step, the telemetry step posts to `POST /api/otlp-token` with the job's OIDC token and a `source` name (the name of the agent run). Older workflows post to `POST /api/agents/{id}/otlp-token` instead, naming the deployment; that route works as before.
3. The server checks the OIDC token (issuer, signature, expiry, audience = `AGBREDO_BASE_URL`). It finds the deployment by the token's repository and workflow file (owner and repository ignore case). The ref is not checked: runs from any branch or tag belong to the deployment.
4. If there is no such deployment, the server asks GitHub, as the GitHub App, for the App's installation on the repository (`GET /repos/{owner}/{repo}/installation`). If the App is not installed, the request is refused and nothing is stored. Otherwise the request creates the deployment: owner and repository as the token spells them (GitHub's own spelling), named `owner/repository · workflow file`, with an empty description, the default threshold (`AGBREDO_DEFAULT_THRESHOLD_USD`, $5 if unset), that installation, and enabled. People can change all of these on the dashboard. Two first requests at once end with one deployment.
5. The server asks GitHub for that run attempt, using the App installation of the deployment, and requires that it matches. A disabled deployment gets no token for a run that has none yet, even if a webhook already recorded the run: recording a run grants it nothing. Only a run that already got a token may get more while its deployment is disabled. The deployment, the run and the token are stored together, or not at all.
6. The first valid request creates the run, or finds the one a webhook recorded (both use the same run ID, so they meet on one row). The first token of a run records on it the event that triggered it (the OIDC `event_name` claim), the ref it ran from (the `ref` claim) and, if the caller workflow calls a reusable workflow, the pipeline and its version (the `job_workflow_ref` and `job_workflow_sha` claims). These replace what a webhook recorded, as OIDC is more exact. Later requests for the same run attempt change none of them.
7. GitHub `workflow_run` webhooks and the poll set the run's status from GitHub (queued, running, completed, failed, cancelled). A run that GitHub concluded as `success`, `skipped` or `neutral` is completed; `cancelled` is cancelled; any other conclusion is failed. A run waiting for a maintainer to approve it (`action_required`, e.g. a pull request from a fork) is not finished: it stays queued, marked as waiting for approval, until GitHub moves it on. The dashboard does not count it as active. Each status change adds one event to the run's history. A finished state is never reopened.
8. Once the run has finished, the server asks GitHub for its jobs and steps, and keeps them on the run (see Jobs and steps).

### Webhook flow

1. GitHub posts each webhook of the App to `POST /api/github/webhook`. The server checks its HMAC signature. A delivery with a bad signature, over 1 MiB, with a missing or long delivery ID, or with an event name over 100 characters is refused and only logged: it is neither archived nor indexed.
2. If `OTLP_FORWARD_URL` is set, the server archives the raw payload, whatever the event, as one OTLP log record: `service.name` = `agbredo-github-webhooks`, the body unchanged as the record body, and the attributes `github.delivery`, `github.event`, `github.action`, `github.repository`, `github.installation_id` and `github.sender` when the payload has them. It is posted to `/v1/logs` with the OpenObserve header `stream-name: github_webhooks`, so webhooks get their own stream. Archiving is best effort, like telemetry forwarding: it never fails the webhook.
3. For a `workflow_run` delivery, the server records the run (see Runs from webhooks).
4. The server indexes the delivery in `webhook_deliveries`: its event, action, repository and App installation, and its outcome. `handled`: it was applied to a run. `ignored`: nothing to do, because Agbredo does not act on that event, or the run belongs to no deployment. `failed`: processing failed, with the error, or the payload did not have the shape of its event.
5. A `handled` delivery is not applied again when GitHub sends it again. A `failed` one is processed again, and so is an `ignored` one. Rows from before outcomes were kept have none; they were all handled.

### Runs from webhooks

Every run of a live deployment is recorded, whether or not it asks for a telemetry token: a run that was skipped, one that failed before its telemetry step, a run of a disabled deployment, a run triggered by a pull request.

1. The server reads the `workflow_run` payload (actions `requested`, `in_progress` and `completed`). The payload is signed, so its facts are used as GitHub gives them, without asking GitHub again. The event header is not signed, so the payload must have the shape of a `workflow_run` event: one of those actions, a `workflow_run` object with its ID, attempt, workflow path and status, and the same repository as the payload's. Otherwise the delivery fails with `400`.
2. The deployment is the live one with the payload's repository (`repository.full_name`) and workflow file (the last part of `workflow_run.path`); owner and repository ignore case. It may be disabled. Webhooks never create deployments. With no such deployment, the delivery is ignored.
3. The run ID is the one the token path uses for that deployment and run attempt. If the run is new, it is created with: GitHub run ID and attempt, the link to the run, the trigger event (`event`), `actor` and `triggering_actor`, a copy of the deployment and its threshold, and the pipeline from the first entry of `referenced_workflows`. A run of a pull request event (`pull_request`, `pull_request_review`, `pull_request_review_comment`) gets no pipeline: it runs the workflow file of the pull request, which the author of a fork controls (the token path refuses pull request events and refs for the same reason). `pull_request_target` runs the base repository's workflow file, and keeps its pipeline. The pipeline path and ref come from that entry's `path` (`org/repo/.github/workflows/x.yml@v1`): the ref is what the caller workflow wrote (e.g. `v1`, not `refs/tags/v1`). The entry's own `ref` field is not used: for a call to the tag `v1`, GitHub has sent `refs/heads/v1`. The run has no ref until a job asks for a token.
4. Each delivery sets the status, adds a status event, and fills what the run is missing: the head branch (`head_branch`: a branch, or a tag name for a tag push), the head commit (`head_sha`), when GitHub started the attempt (`run_started_at`), and, once GitHub has finished it, when (`updated_at`). It never changes what the run has. Runs that a deleted deployment already had are updated too; new runs of a deleted deployment are not recorded.
5. The poll covers lost deliveries: it asks GitHub for each run that has not finished, and fills the same fields. It leaves out runs waiting for approval, which may wait for days; the approval's webhook moves them on, and the poll then follows them again.

Nothing scans GitHub for runs from before the App was installed, or for runs whose deliveries were all lost before they were recorded.

### Jobs and steps

When a run finishes, Agbredo asks GitHub once for the jobs of that attempt, with their steps (`GET /repos/{owner}/{repo}/actions/runs/{run_id}/attempts/{attempt}/jobs`, 100 per page), with the App installation in the run's copy of the deployment. It does not subscribe to `workflow_job` webhooks, which would send a delivery for every job of every workflow in every installed repository.

1. A `workflow_run` delivery that finishes a run wakes the server's worker, which asks GitHub at once; the delivery does not wait for it. The poll's pass, every 30 seconds, does the same for runs that the poll finished, or that a lost wake-up missed. A run waiting for approval has not finished, and is not asked.
2. The call to GitHub is made outside any database transaction. The jobs are then saved in a short one, only if the run still has none.
3. A run is asked once. A run with jobs is not asked again, and neither is one for which GitHub listed no jobs: an empty list is kept as an answer, apart from "unknown".
4. If GitHub does not answer, the run keeps no jobs, and a later pass asks again: after 1 minute, then twice as long after each failure, up to 1 hour. The delays are kept in memory; a restart forgets them. A run is asked only within 24 hours after it finished (GitHub's completion time, or, for a run without it, when Agbredo last changed the run). After that it stays without jobs, so a run whose installation is gone is not asked forever.
5. A pass asks at most 5 runs, newest first, to spare the rate limit of the App installation, which the poll and the token path share.
6. Each job keeps: GitHub's job ID, name, status, conclusion, start and end, runner name and its link on GitHub. Each step keeps: number, name, status, conclusion, start and end. A missing time stays missing. Steps keep GitHub's order and numbers, which may jump (post steps such as 28, 29). A job of a reusable workflow is named after both jobs, e.g. `audit / audit`. At most 50 jobs per run and 100 steps per job are kept, in GitHub's order; names and other texts are cut to 200 characters. A link that is not a `https://github.com/` page is dropped.

### Telemetry flow

1. The server answers the token request of step 2 above with a random token. The token is valid for 6 hours or until the run finishes. Only its hash is stored. It is tied to one run attempt and one agent run.
2. The step puts the token in the environment as `OTEL_EXPORTER_OTLP_HEADERS`. Claude Code then posts OTLP as JSON to `/v1/metrics`, `/v1/logs` and `/v1/traces`. The step also sets `TRACEPARENT` from the token reply. Its trace ID comes from the run ID, so all Claude Code steps of a run attempt share one trace. Traces are a Claude Code beta (`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`).
3. The token alone says which run and which agent run the data belongs to. The server does not read that from the payload.
4. In PostgreSQL the server keeps only token counts (input, output, cache read, cache creation), the cost estimate, the Claude Code version, the models used with token counts per model, the effort levels used, and counts of API errors and rate-limit errors. Models and tokens come from the `model` attribute of the `claude_code.token.usage` and `claude_code.cost.usage` metrics. Effort levels come from the `effort` attribute of those metrics and of `claude_code.llm_request` spans in traces; that attribute is the only thing read from traces. A model or effort level is kept only if it has the form of one, and an agent run keeps at most 16 models and 8 effort levels. With no `effort` attribute, the effort stays missing. It never logs the payload.
5. If `OTLP_FORWARD_URL` is set, the server forwards each accepted payload, unchanged except for added resource attributes: `agbredo.agent.id`, `agbredo.agent.name`, `agbredo.run.id`, `agbredo.source`, `github.repository`, `github.workflow`, `github.run_id`, `github.run_attempt`, `github.run_url`, `github.actor`, `github.triggering_actor`. They come from the token and the run, not from the agent. Attributes starting with `agbredo.` or `github.` that the agent sent are removed. Forwarding runs in the background. If the store is slow or down, the telemetry is dropped and a warning is logged. The agent's request never fails because of it.
6. Delta and cumulative counters are both handled. A repeated export is counted once. A counter that goes down is ignored. Counts are kept per agent run on the run (`sources`), and added to the run totals.

Run status always comes from GitHub, never from telemetry.

A run is registered by its first `workflow_run` webhook or its first token request, whichever comes first. A run without telemetry has no usage: its cost and tokens show as unavailable, not zero.

## Data

| Table | Holds |
| --- | --- |
| `agents` | Deployments: name, description, repository, workflow file, App installation, estimate threshold, enabled. Created by the first valid token request of a repository + workflow file, or by hand on the dashboard. Has an edit revision. Deleting hides it; the next run of its workflow then creates a new one. A repository + workflow file appears once among the deployments not hidden (a unique index; owner and repository ignore case). Older rows also hold a `ref`, which is no longer checked. |
| `runs` | One per workflow run attempt, with or without telemetry. Keeps a copy of the deployment as it was when the run was first recorded, the event that triggered the run (e.g. `schedule`), the ref the run ran from (only for runs that asked for a token), and the pipeline it used with its version (ref and commit SHA), if it used one. From GitHub: the head branch, the head commit, when GitHub started and finished the attempt, whether a queued run waits for approval, and, once it has finished, its jobs and steps (see Jobs and steps; missing for runs that finished more than a day before Agbredo started recording them, or whose jobs GitHub did not give within a day). Older runs have no trigger event and no pipeline, and some have no ref of their own; the run page then shows the ref in their copy, if any. The head branch is shown in its own row, never as the ref. A database trigger blocks changes to that copy. Totals: estimated cost, tokens, API and rate-limit failures. Per agent run: the same, plus the Claude Code version, the models with tokens per model, and the effort levels. The GitHub logins of `actor` (who started the run) and `triggering_actor` (who started this attempt), from GitHub when the run is first seen. |
| `run_tokens` | Hash, run, agent run (column `source`) and expiry of each telemetry token. |
| `otlp_seen`, `otlp_series` | Hashes of exports already counted, and the last value of each cumulative counter. |
| `events` | The run's history: one per GitHub status change. The ID is stable, which makes retries safe. Rows of type `claude.execution` come from the former report route; they still load, and are deleted by hand only. |
| `webhook_deliveries` | One row per webhook delivery that the server accepted, whatever its event: delivery ID, event, action, repository, App installation, outcome (`handled`, `ignored`, `failed`) and the error of a failed one. Rows from before these columns hold only the ID; they were all handled. The raw payload is not kept here. |

Costs are whole microdollars. A missing measurement is stored as missing, not as zero.

## Trust

- **Dashboard:** GitHub OAuth login, an allowlist of GitHub users (`AGBREDO_ADMIN_USERS`), signed session cookie, CSRF token on every form.
- **Runners:** only the short-lived OIDC token. No shared secret, and nothing to register.
- **Which repositories can send telemetry:** any repository where the GitHub App is installed, and nothing else. Installing the App is the only gate. The gate assumes a private App, one that can be installed only on its own account ("Only on this account" in the App settings). A public App could be installed by any GitHub user, who could then create deployments. No person approves a deployment: the first valid run of a workflow in such a repository creates it. The installation ID comes from GitHub, asked by the App itself, never from the runner. To stop a deployment, disable it on the dashboard. To stop a repository, uninstall the App or take the repository out of the installation.
- **Reusable workflows:** accepted. A caller workflow in the target repository may call a pipeline (a reusable workflow) in any central repository. There is no list of allowed central repositories. Trust rests on GitHub. The OIDC token, signed by GitHub, says which repository and caller workflow ran. The server then checks the run with GitHub through the GitHub App, so only runs in repositories where the App is installed can get a telemetry token. The identity is always the caller workflow, taken from the `workflow_ref` claim. The pipeline's `job_workflow_ref` and `job_workflow_sha` claims are never used to decide who is calling. They are only recorded on the run, to show which pipeline version ran.
- **Webhooks:** HMAC signature with the App's webhook secret. A payload with a good signature is trusted as coming from GitHub: its facts are recorded without asking GitHub again. The headers (`X-GitHub-Delivery`, `X-GitHub-Event`) are not signed, so a `workflow_run` payload must have the shape of one. `X-GitHub-Delivery` is not signed, so a replay of a signed payload with a new delivery ID can record a run, or advance its status, with old facts. It cannot reopen a finished run or grant a token. Recording a run from a webhook grants nothing: the run gets a telemetry token only on the same terms as a new run. Raw payloads hold emails, commit messages and other content. They go only to the telemetry store, never to PostgreSQL or to the logs. PostgreSQL keeps only the fields of `webhook_deliveries`. Only records in the `github_webhooks` stream come from Agbredo's webhook archive. `service.name` is not reserved: an agent can send telemetry records with `service.name` = `agbredo-github-webhooks`, and they land in the default stream.
- **Telemetry tokens:** random, per run attempt and per agent run, 6 hours at most, refused once the run has finished. The agent's own process can read its token. With it, it can only send telemetry for its own run.
- **Claude credentials:** never seen by the server. Telemetry arrives as raw OTLP over HTTPS. The server keeps only the fields listed above in PostgreSQL, and forwards the rest to the telemetry store if one is set. From traces it reads only the `effort` attribute of `claude_code.llm_request` spans: no prompts, no content, no other attribute. The telemetry step turns off prompt, response and tool logging. It turns on the Claude account fields (`user.account_uuid`, along with `user.email` and `organization.id` which Claude Code always sends), so the store records which Claude account did the work.
- **Telemetry store:** on the private network only. Agbredo logs in with Basic auth (`OTLP_AUTH_TOKEN`). Runners never get its credentials.

## Limits

- Costs are estimates of API use. The real subscription charge and the remaining quota are unknown.
- The threshold only marks a run. It cannot stop an agent.
- A run is matched by its caller workflow only. Agbredo records which pipeline and version a run used, but does not check them: any pipeline is accepted. A run keeps the pipeline of its first token request, so if the jobs of one caller workflow call different pipelines, the run shows only the first. A run that asked for no token keeps the first of GitHub's `referenced_workflows`, with the ref as the caller workflow wrote it (`v1`), where a token gives the full ref (`refs/tags/v1`). The deployment page counts the two as one version when the commit is the same.
- A run's copy of the deployment (name, threshold, enabled, App installation) is taken when the run is first recorded. That may now be its first webhook, while the deployment was disabled; the copy then says disabled even if the deployment is enabled before a job asks for a token. The token check always reads the deployment as it is now.
- The poll asks GitHub with the App installation in the run's copy of the deployment. If that installation is stale (the App was installed again), the poll fails for that run, and a run whose last webhooks were lost stays queued or running. A run waiting for approval (`action_required`) is not polled: if the approval's webhook is lost, the run stays queued.
- A run recorded only from webhooks has no ref of its own. GitHub's head branch is not a ref: for a tag push it is the tag name, and a pull request run shows its source branch.
- The GitHub App installation is the only gate, and it holds only while the App is private. Anyone who can add or change a workflow in a repository where the App is installed can create a deployment and send telemetry for it, with any pipeline. Install the App only on repositories whose writers are trusted with that.
- Any code that the caller workflow runs with `id-token: write` (the pipeline, or any workflow or action it calls) can get an OIDC token, and with it a telemetry token for that deployment, creating the deployment if it is new.
- The ref is not checked. A workflow file with the deployment's name runs on any branch or tag, so anyone who can push a branch to the repository can get a telemetry token for that deployment. Pull request events and pull request refs (`refs/pull/...`) get no token. Their runs are still recorded from webhooks.
- Telemetry is accepted only as OTLP JSON (`OTEL_EXPORTER_OTLP_PROTOCOL=http/json`), not protobuf.
- Telemetry sent after GitHub marks the run finished is refused. Claude Code sends its last export when it exits, which is before the run finishes. A job that is killed before that loses the last part of its usage.
- Forwarding is best effort. Telemetry dropped while the store is down is not sent again. A repeated export is forwarded again, though it is counted once in PostgreSQL. The same holds for webhook deliveries: one dropped is not archived, and a redelivery is archived again.
- Retention in the telemetry store is not decided yet, for telemetry and for webhook deliveries.
- Run one server replica.
- Deleting a deployment only hides it. The next run of its workflow creates a new one. Disable it instead to refuse its tokens.
- A deployment keeps the App installation it was created with. If the App is uninstalled and installed again, the new installation has another ID, and the deployment's installation must be changed by hand on the dashboard.
- Agbredo does not know when each agent run starts or ends, how long it took, or how its process exited. It sees usage from telemetry and status for the whole run from GitHub.
- A run whose webhooks were all lost before it was recorded, and that asked for no token, is not recorded: the poll only follows runs Agbredo already has.
- Jobs and steps are asked of GitHub once, when the run finishes. A run that finished more than 24 hours before Agbredo started recording jobs, or whose jobs GitHub did not give within 24 hours (for example, its App installation is stale), has none. A run with more than 50 jobs, or a job with more than 100 steps, keeps only the first ones GitHub lists; the run page says when a run reached a limit.
- Stored agents may carry a `mode` field from an earlier version. It is ignored.
